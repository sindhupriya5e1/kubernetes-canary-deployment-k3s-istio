Kubernetes Canary Deployment with K3s & Istio

A hands-on project that demonstrates safer application releases using Docker containers, Kubernetes, Istio traffic splitting, automated image builds, health checks and rollback.

View source on GitHub ↗ Setup runbook CI/CD runs

80 / 20 traffic split

Route most requests to stable and a controlled share to canary using Istio VirtualService.

Fast rollback

Switch traffic back to 100% stable when the canary release needs to be reverted.

CI image pipeline

GitHub Actions builds stable and canary Docker images and publishes them to GHCR.

Observability

Prometheus metrics and a Grafana dashboard track request rates, versions and HTTP errors.

Release flow

The repository contains the manifests, Helm chart and scripts for this workflow:

Git push→GitHub Actions→Docker / GHCR→K3s→Istio 80 / 20

Run and verify

Use the local K3s runbook to deploy to a configured cluster. The local port-forward endpoint is only available from the machine running the command; a public application URL requires a cloud Kubernetes cluster or other public hosting environment.

Useful checks: /health for application health and /metrics for Prometheus metrics.

Verified local canary promotion

Local K3s validation on 1 November 2026: the automated rollout passed all 15 health probes across 80/20, 50/50 and 0/100 traffic stages. The final Istio VirtualService was verified at stable 0% / canary 100%, and a follow-up 20-request in-cluster test returned 20 canary responses.

Scope: these are results from the local test cluster, not a publicly hosted application endpoint. The health-check script is a staged, one-shot gate rather than continuous monitoring.
